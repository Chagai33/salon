# 02 — מודל הנתונים ב-Firestore

> **סטטוס: הצעה. ממתינה לבעל המוצר, 04/10/2026.**
>
> **מה שנקבע:** המסד הוא Firestore, בהכרעת בעל המוצר 04/10. **מה שמוצע כאן:**
> האוספים, השדות ושורש ההרשאות. **מה שחוסם כתיבה:** שלוש ההכרעות הראשונות
> ברשומה [06](06-open-decisions.md), שכל אחת מהן משנה שדות.
>
> המונחים בעברית נלקחים מ-[GLOSSARY.md](../GLOSSARY.md). **מזהה שמסומן ⬜ שם
> שעוד לא אושר.**

## העיקרון: הסניף הוא השורש

**ריבוי סניפים נכנס למודל מהיום הראשון, גם כשרק תל אביב מופעלת.** זו הכרעת
בעל המוצר על ההיקף: לבנות במודל, להפעיל סניף אחד.

**הסיבה שזה לא נדחה:** להכניס `branchId` אחר כך דורש הגירה של כל מסמך בכל
אוסף, כתיבה מחדש של כל חוק הרשאות, וכתיבה מחדש של כל אינדקס. **ולהכניס אותו
עכשיו עולה שדה אחד.**

**ולכן כל אוסף נתונים יושב תחת הסניף:**

```
branches/{branchId}
  members/{memberId}
  shifts/{shiftId}
  activityDays/{dateId}
  accessCodes/{periodId}
```

ו-`users/{uid}` ברמה העליונה, כי משתמש אחד יכול להיות חבר ביותר מסניף אחד.

## `users/{uid}`

**זהות בלבד, בלי תפקידים.** התפקיד שייך לסניף.

| שדה | סוג | הערה |
|---|---|---|
| `uid` | `string` | Firebase Auth UID |
| `displayName` | `string` | |
| `email` | `string` | |
| `phone` | `string?` | E.164, `+9725...` |
| `createdAt` | `Timestamp` | |

⚠️ **`phone` נשמר בפורמט בין לאומי אחד ולא כפי שהוקלד**, כי הוא גם העוגן
לוואטסאפ אם וכאשר ההתראות יורחבו.

## `branches/{branchId}`

| שדה | סוג | הערה |
|---|---|---|
| `name` | `string` | "הסלון שלנו בתל אביב" |
| `city` | `string` | |
| `timezone` | `string` | `Asia/Jerusalem` בכולם |
| `activeDays` | `number[]` | `[0,1,2,3,4]`, ראשון עד חמישי. 📄 |
| `shiftTemplates` | `ShiftTemplate[]` | ראה למטה |
| `spaces` | `Space[]` | ראה למטה |
| `isActive` | `boolean` | תל אביב `true`, השאר `false` עד שיופעלו |
| `icsToken` | `string` | המזהה שבכתובת פיד ה-ICS, רשומה [04](04-activity-days-and-the-ics-feed.md) |

**`ShiftTemplate`** נגזר מהגיליון, שבו שתי המשמרות זהות בכל עשרת החודשים:

```
{ id: "morning", label: "משמרת בוקר", startTime: "10:00", endTime: "14:00" }
{ id: "evening", label: "משמרת ערב",  startTime: "18:00", endTime: "22:00" }
```

⚠️ **תבנית ולא קביעה.** היא זו שמולידה חודש חדש, ולכן נובמבר ודצמבר ייווצרו
ממנה ולא ימתינו למישהו. **ושינוי תבנית אינו משנה משמרת שכבר נוצרה.**

**`Space`**, ארבעה שנמדדו בתל אביב:
`large` חלל גדול, `quiet` חלל שקט, `small` חלל קטן, `offices` משרדים.

⚠️ **ארבעתם נקראו מתל אביב בלבד.** לירושלים ולחיפה לא נבדק.

## `branches/{branchId}/members/{memberId}`

**החברות בסניף, והיא נפרדת מהזהות.** `memberId` הוא ה-`uid` כשיש חשבון.

| שדה | סוג | הערה |
|---|---|---|
| `uid` | `string?` | ריק לחבר שיובא מהגיליון ועוד לא נכנס |
| `displayName` | `string` | השם כפי שהוא מוצג |
| `role` | `"member" \| "manager"` | ⬜ |
| `status` | `"active" \| "pending" \| "inactive"` | ⬜ |
| `rawNames` | `string[]` | הצורות שבהן השם נכתב בגיליון |
| `joinedAt` | `Timestamp` | |

⚠️ **`rawNames` אינו שדה עזר לייבוא, הוא ראיה שנשמרת.** 42 הצורות הגולמיות
ברשומה [01](01-the-spreadsheet-as-it-is.md) אוחדו בהכרעה אנושית, **וכשההכרעה
תתברר כשגויה צריך לדעת מה אוחד לתוך מה.** בלי השדה הזה אין דרך חזרה.

⚠️ **`role` בשני ערכים הוא הצעה ולא הכרעה.** האם "צוות הסלון" שבאתר הוא תפקיד
שלישי לא הוכרע, החלטה 7 ברשומה [06](06-open-decisions.md).

## `branches/{branchId}/shifts/{shiftId}`

**מסמך אחד למשמרת אחת.** `shiftId` הוא `2026-10-08_morning`, כלומר התאריך
והתבנית, **כדי ששיבוץ כפול לאותה משמרת יהיה בלתי אפשרי במסד ולא רק בקוד.**

| שדה | סוג | הערה |
|---|---|---|
| `date` | `string` | `2026-10-08` |
| `templateId` | `string` | `morning` או `evening` |
| `startTime` | `string` | מועתק מהתבנית בשעת היצירה |
| `endTime` | `string` | |
| `assigneeMemberId` | `string?` | **ריק הוא משמרת פתוחה** |
| `assigneeName` | `string?` | שם מוצג, כדי שתצוגת החודש לא תדרוש 60 קריאות |
| `assignedAt` | `Timestamp?` | |
| `assignedBy` | `string?` | החבר עצמו, או המנהל ששיבץ |
| `source` | `"app" \| "import2026"` | מאיפה הגיע |

⚠️ **`assigneeName` הוא כפילות מכוונת, והיא הכפילות היחידה כאן.** בלעדיה כל
פתיחת חודש היא 60 קריאות מסמך. **ומי שמשנה שם חבר חייב לעדכן גם אותה**, כמו
`updateAssignment` ב-Shishi-Shitufi_v3 שמסנכרן שמות.

⚠️ **`date` הוא מחרוזת ולא `Timestamp`, בכוונה.** משמרת היא יום בלוח ולא רגע
בזמן, **ו-`Timestamp` היה הופך את 08/10 לתאריך אחר בכל אזור זמן שאינו ישראל.**

## `branches/{branchId}/activityDays/{dateId}`

**מסמך אחד ליום, `dateId` הוא התאריך.** זה המקום שבו נפתרת הבעיה שבגללה המוצר
נבנה: **העובדה "יש פעילות היום" נשמרת פעם אחת.**

| שדה | סוג | הערה |
|---|---|---|
| `date` | `string` | `2026-10-08` |
| `events` | `ActivityEvent[]` | |
| `salonStatus` | `"open" \| "closed" \| "closesEarly" \| "membersOnly"` | ⬜ |
| `closesAt` | `string?` | רק כש-`salonStatus` הוא `closesEarly` |
| `note` | `string?` | |

**`ActivityEvent`**: `title`, `space`, `startTime`, `endTime`.

⚠️ **הכוכבית, הצבע והרשימה אינם שדות.** הם נגזרים: **יום הוא יום פעילות אם
ורק אם `events` אינו ריק.** זה מה שמונע את 16 הפערים שנמדדו בגיליון, רשומה
[01](01-the-spreadsheet-as-it-is.md).

⚠️ **`salonStatus` הוא שדה עצמאי ואינו נגזר מ-`events`.** נמדד: ב-13/09 הסלון
סגור לראש השנה ואין בו אירוע, **וב-01/01 יש מסיבת סילבסטר והסלון סגור באותו
יום.** שני המצבים חיים זה לצד זה.

## `branches/{branchId}/accessCodes/{periodId}`

**הקוד שהמנהל מגדיר.** `periodId` הוא `2026-10`.

| שדה | סוג | הערה |
|---|---|---|
| `code` | `string` | |
| `validFrom` | `string` | |
| `validTo` | `string` | |
| `setBy` | `string` | מי הגדיר |
| `setAt` | `Timestamp` | |

## ⚠️ אין אוסף זכאות, וזו הכרעה

**הזכאות נגזרת ואינה נשמרת.** חבר זכאי אם יש לו משמרת בחודש, וזו שאילתה אחת
על `shifts` לפי `assigneeMemberId` וטווח `date`.

**הסיבה:** זכאות שנשמרת כשדה היא זכאות שיכולה להתיישן. חבר שביטל משמרת והשדה
לא התעדכן **הוא חבר שרואה קוד שאינו שלו**, וזה אזור ליבה ב-`CLAUDE.md`.

⚠️ **ההגזרה הזו תלויה בהכרעה 1 ברשומה [06](06-open-decisions.md):** אם "משובץ"
יתברר כ"משמרת שהתקיימה" ולא "שיבוץ", צריך שדה `completed` על המשמרת, **והוא
לא נכנס לכאן לפני ההכרעה.**

## חוקי ההרשאות: השורש, לא הנוסח

**הנוסח ייכתב עם `firestore.rules` ויאומת מול האמולטור.** מה שנקבע כאן הוא
העקרונות:

1. **חבר קורא את הסניף שהוא חבר בו, ולא סניף אחר.**
2. **חבר כותב שיבוץ של עצמו בלבד**, ורק למשמרת פתוחה.
3. **רק מנהל כותב `accessCodes`, `activityDays` ו-`members`.**
4. **`accessCodes` אינו נקרא ישירות על ידי חבר.** הזכאות נבדקת לפני החשיפה,
   וחוק מסד לבדו אינו יכול לבדוק אותה. החלטה 3 ברשומה [06](06-open-decisions.md)
   תכריע אם זו פונקציית ענן.
5. **פרטי קשר של חבר נקראים על ידי החבר עצמו ועל ידי מנהל הסניף.**

⚠️ **הנקודה הרביעית היא החור היחיד שידוע כאן מראש.** `allow read` על
`accessCodes` לפי חברות בסניף **היה חושף את הקוד לכל חבר, זכאי או לא**, וזה
בדיוק הכשל שהמוצר בא למנוע.
