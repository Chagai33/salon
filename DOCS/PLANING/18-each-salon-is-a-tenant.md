# 18 — כל סלון הוא טננט, ומי פותח אותו הוא המנהל שלו

> ✅ **סטטוס: נבנה ונמדד, 05/10/2026. 28 בדיקות מול אמולטור, כולן עוברות.**
>
> ⚠️⚠️ **והחוקים השתנו אחרי הפריסה. צריך להדביק אותם שוב.**

## מה בעל המוצר ביקש

> "תראה שיש איך לפתוח לכל סלון טננט משלו עם כל מה שצריך מתחת, ואולי אפילו
> ניווט באתר לפי סלונים."

## מה שכבר היה נכון, ומה שלא

**המודל היה מקונן מההתחלה.** כל מה ששייך לסלון יושב תחתיו:

```
branches/{branchId}/members/{uid}
branches/{branchId}/shifts/{shiftId}
branches/{branchId}/activityDays/{date}
branches/{branchId}/accessCodes/{codeId}
```

**וכל אוסף כזה נשמר ב-`isMember(branchId)`.** כלומר הגבול היה קיים בחוקים,
רשומה [02](02-the-data-model.md).

⚠️ **ומה שלא היה: האפליקציה.** `DEFAULT_BRANCH_ID = 'tel-aviv'` ישב בכל קריאה,
`ensureDefaultBranch()` רץ בכל כניסה ויצר את תל אביב, לא הייתה דרך לראות סלון
אחר, **ולא הייתה כתובת שאומרת באיזה סלון אני.**

**כלומר המודל היה רב סלוני, והמוצר היה חד סלוני.**

## ⚠️⚠️ הבעיה הקשה: מי המנהל הראשון

**מי שפותח סלון חייב להיות המנהל שלו**, אחרת אין בו אף אחד שיאשר חברים, ואין
דרך להגדיר מנהל בלי מנהל.

⚠️ **וההפך מסוכן בדיוק באותה מידה:** אם מותר לכתוב לעצמך `role: manager`, כל
מי שנרשם הופך למנהל של כל סלון, **וקורא את קוד הכניסה ואת רשימת החברים של
כולם.**

**זו ביצה ותרנגולת שנייה בפרויקט הזה.** הראשונה הייתה רשומה
[17](17-the-first-sign-in-could-never-work.md), ושם הפתרון היה להפריד `get`
מ-`list`. כאן הוא אחר.

### הפתרון: `getAfter`, ושני חוקים שתלויים זה בזה

**פתיחת סלון היא כתיבה אחת של שני מסמכים**, אצווה. ו-`getAfter` בחוקי Firestore
בודק את המצב **אחרי** שהאצווה כולה נכתבה.

**על מסמך הסלון:**

```
allow create: if signedIn()
  && request.resource.data.createdBy == request.auth.uid
  && getAfter(/databases/$(database)/documents/branches/$(branchId)/members/$(request.auth.uid))
       .data.role == 'manager';
```

**ועל רשומת החבר, בכיוון ההפוך:**

```
|| (
  request.resource.data.status == 'active'
  && request.resource.data.role == 'manager'
  && !exists(/databases/$(database)/documents/branches/$(branchId))
  && getAfter(/databases/$(database)/documents/branches/$(branchId))
       .data.createdBy == request.auth.uid
)
```

**מה שזה אומר בפועל:**

| הניסיון | התוצאה |
|---|---|
| אצווה שיוצרת סלון חדש ואת הפותח כמנהל | ✅ עוברת |
| סלון בלי מנהל באותה אצווה | ❌ נדחה |
| סלון עם `createdBy` של מישהו אחר | ❌ נדחה |
| ⚠️ **מינוי עצמי כמנהל בסלון קיים** | ❌ **נדחה**, כי `exists` נכון |
| ⚠️ **אצווה שמנסה לדרוס מסמך של סלון קיים** | ❌ **נדחה**, מאותה סיבה |
| הצטרפות רגילה לסלון קיים | ✅ עוברת, כ-`pending` |

⚠️ **ושתי השורות האלה תלויות זו בזו. שינוי באחת בלי השנייה פותח חור.** זה כתוב
בקובץ עצמו, ליד שתיהן.

## מה שנמדד

**`test/rules/branches.test.mjs`, 12 בדיקות חדשות.** שש על פתיחת סלון, ושש על
הגבול בין סלונים:

```
⚠️ וחבר של סלון אחד אינו קורא את החברים של האחר
⚠️ ואינו קורא את המשמרות של האחר
⚠️⚠️ ואינו קורא את קוד הכניסה של האחר
⚠️ ומנהל של סלון אחד אינו עורך את ההגדרות של האחר
⚠️ ואינו מאשר חבר בסלון האחר
```

**כל בדיקה כזו קוראת קודם מהסלון שלה ורואה שזה עובר, ואז מעבר לגבול ורואה
שזה נדחה.** בלי החצי הראשון היא הייתה עוברת גם אם החוקים חוסמים הכל.

**סך הכל 28 בדיקות, כולן עוברות.**
