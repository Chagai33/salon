# 20 — מי מורשה לפתוח סלון, ושני באגים שבעל המוצר מצא

> ✅ **סטטוס: תוקן ונמדד, 05/10/2026. 33 בדיקות מול אמולטור, כולן עוברות.**
>
> **שלוש השאלות נשאלו על ידי בעל המוצר**, ושתיים מהן היו באגים.

## 1. ⚠️⚠️ "אבל מי יכול לפתוח סלון?"

**התשובה שהייתה נכונה כשהשאלה נשאלה: כל מי שנכנס ב-Google.**

**רשומה [18](18-each-salon-is-a-tenant.md) בנתה את פתיחת הסלון ובדקה אותה
ב-12 בדיקות, וכולן בדקו את המנגנון:** שמי שפותח נכתב כמנהל, שאי אפשר לפתוח
בשם מישהו אחר, שאי אפשר למנות את עצמך בסלון קיים.

⚠️ **ואף אחת מהן לא שאלה אם מותר לו לפתוח בכלל.** הבדיקות הוכיחו שהמנגנון
עובד, **ולא שהמדיניות נכונה.** זה הפער, והוא לא נמצא בבדיקה אלא בשאלה.

### התיקון: אוסף שנכתב בקונסולה בלבד

```
match /platformAdmins/{adminId} {
  allow get: if signedIn() && adminId == request.auth.uid;
  allow list: if false;
  allow write: if false;
}
```

**ו-`allow write: if false` אינו פשרה.** אין דרך להוסיף מנהל מערכת מתוך
האפליקציה, **בשום מצב ובשום תפקיד.** רק בקונסולה.

**ויצירת סלון דורשת אותו:**

```
allow create: if isPlatformAdmin()
  && request.resource.data.createdBy == request.auth.uid
  && getAfter(.../members/$(request.auth.uid)).data.role == 'manager';
```

### ⚠️ ומה שזה נותן לו, במלוא ההיקף

**מנהל מערכת יכול לערוך רשומת חבר בכל סלון.** זו הדרך להגדיר את המנהלת
הראשונה של סלון שנוצר לפני החוק הזה, **והיא גם אומרת שהוא יכול להפוך את עצמו
למנהל של כל סלון**, אם יש לו שם רשומת חבר.

**זה מה ש"מי שמפעיל את המערכת" אומר, וזה נאמר כאן במפורש ולא מוסתר.**

⚠️ **ומה שהוא לא יכול, ונמדד:** לקרוא את קוד הכניסה או את רשימת החברים של
סלון שאינו חבר בו. **ההרשאה לפתוח סלון אינה הרשאה לראות מה בתוך סלון.**

⚠️ **ו"מנהל מערכת" הוא מונח חדש שאין לו שורה ב-`DOCS/GLOSSARY.md`.** הוא אינו
מופיע באף מסך, ולכן אין עדיין שם במוצר. **הוספת השורה ממתינה לבעל המוצר.**

## 2. "והאם מנהל סלון א יהיה מנהל בסלון ב?"

**לא.** התפקיד יושב על רשומת החבר, והרשומה יושבת תחת הסלון:

```
branches/jerusalem/members/{uid}  →  role: 'manager'
branches/tel-aviv/members/{uid}   →  role: 'member'
```

**שש בדיקות מודדות בדיוק את זה**, וכל אחת קוראת קודם מהסלון שלה ורואה שזה
עובר, ואז מעבר לגבול ורואה שזה נדחה:

```
⚠️ ומנהל של סלון אחד אינו עורך את ההגדרות של האחר
⚠️ ואינו מאשר חבר בסלון האחר
```

## 3. ⚠️ "הכפתור החלפת סלון בכלל לא עובד"

**נכון, ולא עבד בכלל.**

**הקישור הצביע ל-`/`**, ו-`/` מפנה אוטומטית לסלון היחיד של מי שחבר בסלון אחד.
**כלומר הלחיצה חזרה מיד לאותו מסך**, ולמשתמש זה נראה כמו כפתור מת.

**התיקון:** `/salons` הוא נתיב מפורש שתמיד מציג את הרשימה, ו-`/` נשאר הכניסה
החכמה.

### ⚠️⚠️ ואיך זה לא נתפס

**הבדיקה שהרצתי רנדרה את `SalonsPage` לבד**, עם ה-Store האמיתי. היא עברה,
**והכפתור שלא עבד יושב ב-`TopBar` ולא ב-`SalonsPage`.**

**זה אותו דפוס בדיוק של רשומה [16](16-the-selector-that-looped.md):** שם
הבדיקה עקפה את ה-Store, **וכאן היא עקפה את עץ המסכים.** ורשומה 16 כבר כתבה
את המשפט הזה: *"תצוגת בדיקה שאינה עוברת דרך ה-Store אינה בדיקה של המסך."*

**מה שהשתנה:** `Shell` מיוצא מ-`App.tsx` בלי המאזינים, **ועץ המסכים כולו
נרנדר בדפדפן ונלחץ בפועל:**

| מה נמדד | התוצאה |
|---|---|
| הקישור מצביע ל-`/salons` | ✅ |
| הרשימה מוצגת לחבר בסלון אחד | ✅ |
| **לחיצה אמיתית על הכפתור** מציגה את הרשימה | ✅ |
| פתיחת סלון אינה מוצגת למי שאינו מורשה | ✅ אפס מופעים |
| `/` עדיין נכנס ישר לסלון היחיד | ✅ וזה מכוון |
| גלילה אופקית ברוחב 390 | ✅ אין |

## מה שנלמד

**שתיים מהשלוש לא היו שאלות אלא באגים, ושתיהן נמצאו על ידי בעל המוצר.**

⚠️ **והמשותף להן: בדקתי את מה שבניתי, ולא את מה שהמשתמש עושה.** המנגנון של
פתיחת סלון נבדק ל-12 בדיקות ואיש לא שאל מי מורשה, **והכפתור נבדק ברכיב שהוא
אינו יושב בו.**

**זו הפעם השלישית בפרויקט הזה שהתבנית הזו חוזרת**, רשומות
[16](16-the-selector-that-looped.md),
[17](17-the-first-sign-in-could-never-work.md), וכאן.
